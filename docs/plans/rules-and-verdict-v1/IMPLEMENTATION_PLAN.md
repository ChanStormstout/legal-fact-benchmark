# 规则与请求判断V1：实施、实验与停止条件

日期：2026-10-01。状态：**用户已授权启动；两案资源／格式检查失败，按§3.1停止在P1**。实际代码、配置和结果见[阶段报告](../../../outputs/rules-verdict-v1/report-zh.txt)。下文保留完整设计目标，未标为完成的模块仍是计划；运行配置以版本化输出目录为准。配套[完整pipeline](PIPELINE.md)说明组件语义。

## 1. 首轮交付与范围

首轮先在最多5个已有开发案件中完成“允许事实 → 明文规则 → 条件绑定 → 法源与请求结论”，再在最多10个未参与该方法开发的新案件上检查。新案保持固定方法，遇到失败仍计入；不为了凑正例或展示优势换案。没有足够兼容来源就报告实际规模，不自动扩大到100案。

首个任务优先选择腾退中的一个具体争点。按已有来源清单顺序检查法律制度、法域、版本和程序阶段，选第一个具有至少3个完整开发来源的兼容组，取最多5案；关联不明保留标记。这里的3案只是决定先实现哪个材料组的工程门槛，不是证明可归纳规则的样本量。若没有这样的组，先对固定顺序首个完整开发案例完成明文规则提取与接口检查，并报告跨案条件不足，不虚称完成跨案实验。

优先检查转租腾退组，因为已有关系诊断提供对象材料；若这些案件实际适用不同制度或程序，则不能拼在一起训练一条统一规则。具体选定法条、日期标准和实体结论须由来源核对确定，本计划不虚构统一适用的印度法律标准。

交付包括：任务定义、来源与划分清单、定义卡/规则库、抽取及执行代码、法源检索索引、冻结配置、模型原始输出、条件与裁判轨迹、逐题评测、中文报告和GitHub审阅包。明文规则、描述性模式和归纳假说分别汇总。

## 2. 保留现有工作，新增独立组件

使用当前`research/rules-and-verdict`分支，旧main及实验目录不动。先记录父提交、当前未提交变更清单和源码哈希；新实验还需保存实际运行源码快照，不能只记有未提交修改的commit。`legal_bench/local_chunk_v11.py`属于未完成旧草稿，本计划不将其视为基础实现，也不改动。

拟新增`legal_bench/rules_verdict_v1/`，以下接口以文件输入输出为准，不让模型直接执行SQL、Python或任意生成代码。

| 模块 | 实现内容 | 复用与必要限制 |
| --- | --- | --- |
| `contracts.py` | CaseTask、断言、关系、RuleCard、轨迹和结果Schema；所有枚举及版本 | 保存字段级未知、技术失败答案null；同名旧对象通过显式适配 |
| `source_views.py` | 稳定位置、允许输入视图、受保护答案区、来源与划分清单 | 原文只读；打印每个下游实际读取的片段/内容哈希 |
| `runtime.py` | 参数化MLX运行、Schema掩码、tokens/耗时/内存、恢复与失败 | 复用v3机制；不调用其固定旧输出路径 |
| `extract.py` | 顺序分块、多类型断言、对象提及、一次跨块整理 | 使用新格式；不继承旧20条数组总上限和无时间字段假设 |
| `normalize.py` | 定义卡匹配、原始/抽象双视图、family、对象别名 | 合并有依据；未归类与争议可保留 |
| `authority_index.py` | 法源单元、父片段、版本及定义/例外依赖；FTS5与向量索引 | 法律原文完整保存；检索片段不替代完整适用上下文 |
| `rule_cards.py` | 明文提取、来源核对记录、规则来源性质、适用边界 | 自然语言卡先于程序表达；文本保留与机器执行分开 |
| `rule_induction.py` | 至多3候选、至多6近邻、1次局部修订、来源限制 | 可选阶段；材料不足时输出未执行原因 |
| `pattern_adapter.py` | 复用双事件候选、规范化去重、支持统计及见证 | 描述性模式不升级为法源；无需重挖整批旧案 |
| `retrieve.py` | 原文/结构查询、BM25、向量、RRF、重排、依赖补全 | 输出全部排名、范围排除原因和预算截止位置 |
| `compile_rules.py` | 将已选RuleCard编译为受限条件树，检查变量/类型/范围 | 未支持部分不能被静默省略；无语义修复权限 |
| `apply_rules.py` | 带来源的绑定表、AND连接/OR分支、显式反证、例外与未知 | 适配现有字段/关系函数；新增组合层，不改旧实验语义 |
| `decide.py` | 同一9B读取应用表和原文，输出逐请求判断与依据 | 模型预测与程序能支持的法律效果分开 |
| `evaluate.py` | 法源、条件、绑定、请求结果、失败与成本分别评分 | 不以匹配量/UNKNOWN下降代替准确性 |

未来输出根建议为`outputs/rules-verdict-v1/`。在首次产生实验文件前，显式登记到`docs/repository-artifacts.json`。本次只新增设计文档，没有创建该运行目录。

拟定运行目录如下，每次运行写新的run_id；来源可通过哈希引用现有不可变文件，不复制整个数据集。

```text
outputs/rules-verdict-v1/
  protocol/       # 任务、划分、允许输入、评分与预算
  sources/        # 来源清单和必要的新来源；已有来源用引用
  definitions/    # 任务类别及映射
  authorities/    # 法源单元清单、原文/版本、索引说明
  rules/          # 明文规则、候选、反例、形式化覆盖
  prompts/        # 模板、完整示例、实际渲染后的输入
  references/     # 模型参考、原文证据、未知和争议
  freeze/         # 文件哈希、依赖锁、模型revision、源码快照
  runs/<run_id>/  # 原始输出、导入、检索、执行、判断、评分、成本
```

计划中的CLI顺序是`prepare → extract-dev → build-authorities → build-rules → compile → check-dev → freeze → reference-new → run-new → evaluate → report`。它不是当前可执行命令。每步根据输入哈希与成功记录恢复，已有成功任务不重复发给网页或本地模型；失败保留，是否重试受该轮协议限制。

## 3. 提示词、格式与运行配置

### 3.1 固定生成模型，检索模型独立锁定

| 设置 | 建议沿用/采用 | 冻结前检查 |
| --- | --- | --- |
| 生成模型 | `mlx-community/Qwen3.5-9B-4bit` | 已有revision `8b2b98c00a6b4d291155e4890773ca8f769aee53` |
| 生成框架 | 项目MLX-VLM 0.7.4，已有专用环境 | 保存完整依赖锁和实际生效参数 |
| Schema约束 | 已有MLX logits hook + lm-format-enforcer 0.11.2 | 新Schema在开发例上检查掩码与完成停止；失败不静默关闭 |
| thinking/采样 | 关闭thinking；temperature 0，top_p 1，top_k 0，min_p 0，repetition_penalty 1 | 校验框架支持并保存实际值；seed 20261001 |
| 每次总上下文 | 初始32,768 tokens（输入+最大输出） | 用chat template精确计数，不等同于本机可承受承诺 |
| 抽取输出 | 每块最多8,192 tokens；跨块整理最多4,096 | 初始Schema每块最多32断言/64对象提及/32关系；达到上限须标记可能未覆盖，不当作完整抽取 |
| 规则/最终回答输出 | 明文规则或归纳最多4,096；请求回答最多4,096 | 只输出结构化字段、简短依据和出处；不要求长篇推理 |
| 分块 | 来源最多4,000 tokens，重叠400；保持句子边界 | 所有允许片段必须进入至少一块；过长单片段单独预检 |
| 单调用超时 | 初始1,200秒 | 超时输出保留；技术失败答案null |
| 向量模型 | Qwen3-Embedding-0.6B，1024维 | 实施时解析具体revision，固定tokenizer/依赖；不填未经核对的SHA |
| 重排模型 | Qwen3-Reranker-0.6B | 同上；记录yes/no评分实现，不使用生成的口头置信度 |
| 检索环境 | 独立`.runtime/retrieval-v1`，本地Transformers，先CPU运行 | 无CUDA/FlashAttention假设；逐模型加载、结果缓存；设备或精度改变另记版本 |

每次只加载一个大模型、处理一个案件。先在最多2个旧开发例上检查新Schema和资源，每例各跑一次新版本抽取与回答；成功标准是完成、可解析、引用有效、可执行，不是答对。格式只做内容明确不变的转义/外包装修复并记录；内部含义或缺字段不猜补。达输出上限或记录上限的遗漏风险保留，不能靠截断JSON冒充完成。

若资源/格式失败，两例检查后停下并交付故障；不继续跑新案，也不在同案无限调整。开发修订另开版本后再由明确的实施请求决定下一轮。不得自动切到35B、vLLM、网页受测模型或付费API。

检索模型未就绪时可以完成并报告BM25基线，但必须标为BM25；不能把未运行的混合检索写成已采用。同样，模型revision和新Schema最终上限应在开发检查后冻结，而非根据新案答案调参。

### 3.2 每类prompt包含什么

| 阶段 | 输入必须包含 | 输出及禁止事项 |
| --- | --- | --- |
| 事实抽取 | 任务定义、允许状态、字段说明、完整合格示例、本块原文和片段ID | 来源断言/对象提及/关系/未知影响字段；可OTHER，不补法律结论 |
| 跨块整理 | 已抽记录、全部相关提及与原文窗口、已有ID | 别名与关系建议及出处；未见身份依据不合并、不分配群体行为 |
| 明文规则 | 完整相关条款及上下文，或判决完整理由范围、争点和阶段 | 自然语言规则、条件性质、例外、来源；区别采用/引述/否定 |
| 跨案候选 | 兼容规则材料包、来源性质、候选预算、反例分类 | 新增概括及支持/反例；不按多数或预测分数赋予法律效力 |
| 请求回答 | 相同允许事实、固定问题、法源材料；按方法增加抽取/执行表 | 请求结果、对象、证据与缺口；不能擅自把必要条件变充分条件 |
| 网页参考 | 完整来源、允许/受保护片段清单、相同任务和标注要求 | 输入内条件依据、实际判决另列、法源作用、其他组合和缺口；不得看到本地答案 |

示例使用与当前案无关的虚构人物和对象，填满结构，不使用省略号或“选项A/选项B”这种字段占位。不同示例分别展示肯定、否定、仅类型可靠和关系未知；不在当前案件prompt里提供正确组合。Schema固定结构，字段定义限定语义，原文证据限定内容，三者各有作用。

### 3.3 输入公平与长文本

所有主方法读取同一允许来源范围，不截断判决，不用网页摘要替代原文。新任务的允许输入可按预先规定的判断阶段排除目标裁判理由，这属于任务定义，须记录全部排除项；不能按模型是否答对决定删哪段。

在看模型答案前，按各主方法的完整prompt与输出预留检查最大上下文。对于需要最终LLM回答的同法源比较，若任何一个方法因全文/共同法源无法装入32,768，整组标记为输入预算不适配并保存各自预检结果，不只给某个方法更短材料。抽取分块仅解决抽取生成，不假称它让直接回答也获得无限上下文。

固定法源包按排名与完整单元构成，不能按正确答案选取。如果为共同预算减少法源，所有方法使用同一减少结果，并报告被排除的单元和依赖未覆盖；必要依赖不完整的规则不得参与确定性结论。不存在静默只截掉但书的步骤。

同信息比较不等于同调用量。主报告列出抽取、整理、检索、最终回答各阶段输入输出tokens、墙钟时间、峰值内存与复用情况；若主方法多用调用，需要明确这一成本。算力预算严格配平属于后续独立实验，不能以固定同一模型冒充预算相等。

## 4. 实施顺序与每阶段完成条件

| 阶段 | 具体工作 | 完成后得到什么 | 停止/降级条件 |
| --- | --- | --- | --- |
| P0 任务与来源 | 选定一个兼容争点，登记最多5旧案、最多10新案的候选顺序；定义输入时间、标签、关联和法源库范围 | `task_spec`、分组、允许来源清单；新案答案尚未供方法开发读取 | 来源或法律范围不明确，先报告缺口；不拼接不兼容制度 |
| P1 契约与抽取 | 实现新Schema、分块、ID和一次整理；接入字段级未知；用最多2旧例检查格式/资源 | 可恢复抽取管道、原文可追踪记录和冻结候选配置 | 技术未通过就不启动新案，语义错误记录而不无限返工 |
| P2 明文规则与检索 | 处理其余开发例；取得完整法源、提取至多5张当前争点需要的明文规则卡、建立BM25/向量/重排 | 有出处的规则与索引，必要/充分/例外清楚 | 超出5卡覆盖就显式限定“本阶段覆盖”，不能省略后仍输出完整请求结论 |
| P3 条件执行 | 编译开发规则、共享绑定、例外及证据状态；复用关系题和必要合成反例 | 可执行应用表；原文、状态、对象错误可定位 | 真实规则不能表达则文本判断/UNSUPPORTED；不放宽题意 |
| P4 开发比较与冻结 | 跑E0—E2开发对照；可选归纳至多3候选；定好所有配置、任务、评分与补查关闭 | 源码快照、prompts、规则与索引哈希、固定样本顺序 | 无完整链也提交失败报告，不自动扩大样本 |
| P5 新案参考与一次运行 | 先建立参考并封存，再运行E1—E3；不得将参考注入运行入口 | 最多10案的全部方法结果与失败、有限分歧检查 | 难案不替换；只有来源缺失按预定候补序补入 |
| P6 结果与后续决策 | 最多核查3项高风险分歧；报告方法、条件、法源与成本 | 中文报告、表格、轨迹、网页审阅包 | 本轮结束；规则/模型/GNN/反馈均不自动开下一轮 |

规则卡的5张上限控制首轮开发工作量，不授权遗漏一个请求所需的其他法律条件；若完整请求超出覆盖，仍可完成已覆盖争点的条件实验，同时明确请求判断未完成。

程序测试集中于真正容易出错的语义：同合同/不同合同；不同假设分支；类型已知但日期未知；群体成员与身份；显式否定与未找到；冲突；一个组合失败而另一个成功；未知例外；必要条件误作充分条件；五个条件中一个失败；技术失败答案null；来源与受保护答案不混入输入。新增组件各跑相关测试，集成后跑一次全套；无代码变化不重复跑旧测试。

## 5. 先把参考答案与受测方法分开

旧三个关系问题、v3/v10及其来源继续作为开发诊断；它们不能直接提供找法和请求结果的新标签。这里只新增目标争点需要的少量参考，不重做整份判决的所有事实标注。

普通High网页对话按案读取完整判决和允许输入清单，保存两层记录。第一层仅根据允许输入判断具体条件、对象、关系及缺口；第二层单独记录法院实际采用的法源、理由与结果，依据可来自受保护答案区。第二层材料不得被当作第一层在预测时已经知道的事实。两层都在本地模型运行前保存并哈希封存。

法源参考标为“决定性/相关/明确不相关/未判断”，解释相关性和范围。法院引用列表只构成已观察参考的一部分，不能据此认定未引用来源无关。参考记录完整绑定、支持引文、反对依据和其他候选检查；无法判断不强行标签化。法律上存在合理解释分歧时，保存可接受解释和分歧，不能将单一模型偏好称为唯一正确法律答案。

预算为最多5个开发案任务、最多10个新案任务，必要时一个集中分歧任务；每任务普通High，记录实际型号、设置、URL、时间、prompt与下载JSON。已有完全满足新任务要求的产物直接复用。开发任务可同时核对该案规则材料，新案任务不能看本地输出。只是形式错误优先本地无损处理；不为了所有字段完整连续追问。

严格意义上没有人工金标准：统一标记“模型生成并依据原文复核”。实际裁判结果是历史记录，预测到该结果不等于证明裁判正确。语义评分以这些模型参考为基础，另列程序验证和直接来源证据。

## 6. 实验矩阵：每一步只回答一个可解释问题

### E0：程序与格式能否按定义工作

先做必要确定性测试与2例资源/格式检查。可执行不等于事实正确；以当前案预期答案作为格式准入条件会造成选择偏差，因此禁止这样做。

### E1：结构表示能否帮助找法

固定法源库和重排器，比较BM25、原文查询的BM25+向量混合检索、原文与结构查询的混合检索。保存每路候选、重排前后名次和依赖补全。使用相同每路/总候选上限；同时报告多路查询带来的额外成本。法源相关性和范围兼容分别评价，条件未满足的控制性法源仍可算检索相关。

指标包括已知相关法源Recall@8/@24、已知决定性法源是否遗漏、具体条款/版本错误，以及前8项中已评为相关/不相关/未判断的数量。已知相关集合不完整时，Recall称为“对已知参考的覆盖”；有未判断项不报告完整Precision或把它们当0计算nDCG。若条件允许，可在固定小池内标全再报告该池排名指标，不能虚称穷尽全部法律。

### E2：同一法源下，结构与执行是否帮助应用

共同法源包由冻结的原文混合检索规则选取，不用参考答案指定。实际对照如下。

| 方法 | 模型看什么 | 用于回答 |
| --- | --- | --- |
| A0 直接判断 | 允许的原文事实、请求与争点 | 不接入外部知识的基础表现；不是与RAG相同信息的对照 |
| A1 文本RAG | 同一原文 + 共同法源原文/历史理由 | 获取相同外部法律材料后，直接LLM怎样表现 |
| A2 结构文本 | A1材料 + 本地抽取的事实/关系及相同规则卡的文字形式 | 抽取和规则组织本身是否有帮助；不执行条件 |
| A3 条件执行 | A2全部信息 + 由这些事实/规则执行得到的绑定与证据表 | 在相同抽取和规则解释下，程序执行带来的变化 |

A2与A3使用同一个本地抽取版本和规则卡；A3不能使用网页参考事实。A1可读同一知识库中对应的原始条文/理由，不凭空少给某段法律材料。A2/A3多了源自这些材料的处理结果，差异正是要测的组件，不另加答案。

固定事实另做两个本地诊断：忽略对象关系只看条件类型共现；把字段未知当作否定。它们不是完整法律判断方法，不能将全部多出的候选称为错误。只在有参考支持的具体条件/绑定上判断误接或错误确定。抽取问题与执行问题仍难区分时，使用网页的相关参考事实执行一次诊断，单独列为“参考事实输入”，不当作端到端成绩。

### E3：完整方法比较

比较A1使用原文检索得到法源、A3使用原文+结构检索得到法源的完整流程。它测方法组合，不单独归因于某个组件；E1/E2用于解释变化。已完成且输入/配置哈希完全一致的调用直接复用，不能为了成本表重复运行。

规则库的第一次比较只使用明文规则。若开发材料足以支持跨案候选，另外登记“增加候选规则”对照，保留候选地位，使用同样历史知识范围和预算。若不足则跳过并报告，不把描述性模式改名成归纳规则来凑实验。

E3之后本轮结束。有限补查、图检索或换模型是下一轮单独比较，不在看到新案错误后直接加组件重算并继续称独立结果。

### 统一评分与有限复核

按实际案件数、纠纷关联情况和分析单位数同时报告；同案多条件不当作多份独立样本。首轮给出分子/分母和逐案表，不用小样本显著性证明普遍优势。法源、条件、绑定、结果和来源解释分开。

| 参考情况 | 方法结果 | 记录什么 |
| --- | --- | --- |
| 明确满足某条件/完整规则 | 未找到或未知 | 漏检或未完成；追踪抽取、绑定、状态或执行原因 |
| 规定材料中明确未找到，且无关键待定组合 | 声称有完整匹配 | 误报；具体检查对象与来源 |
| 关键证据确实不足/有争议 | 无依据给确定判断 | 过度判断；与法律举证规则产生的有依据后果分开 |
| 声称匹配但对象/引文不成立 | 结果标签碰巧一致 | 不计为有支持的成功匹配 |
| 运行失败 | null | 单独记录失败并保留在总题数分母；不改成UNKNOWN |
| 请求结果与实际裁判相同 | 理由/条件不成立 | 结果一致、理由未获支持，不能宣称完整法律推理正确 |

技术失败和任务本身语言不支持分别明示，部分成功不能遮盖关键条件无法执行。每个错误首个发生位置记为来源缺失、抽取、身份/关系表示、规则解释/编译、检索、执行、开放法律判断或多重原因；不能凭后端出现UNKNOWN就断定执行器坏了。

新案分歧最多复核3项，固定顺序优先无依据MATCH、明确正例漏检、原文足够却未知；同类按预先样本顺序。只核对相关原文与分歧，可合成一个普通High任务，每项一次。修正参考保留旧版并统一重评分所有方法；方法问题只记录下一轮，不能本轮修后再把样本称未参与开发。

## 7. 后续组件的启动条件与具体候选

| 候选 | 什么时候值得启动 | 实际要比较什么 |
| --- | --- | --- |
| 有限补查 | 主要失败是输入/法源中已有证据未被当前步骤找到 | 0轮 vs 1轮、每案最多2缺口，同材料；不查询目标答案区 |
| 监督对比学习 | 定义稳定，已有足够经来源复核的同类/异类表达 | 冻结0.6B表示 vs 训练表示；混淆率和下游绑定，训练不见评测 |
| 预训练GFM-RAG | 图适配保存状态/来源，本机运行可行，检索仍漏关键链 | 冻结checkpoint vs 文本检索；同语料、同候选规模、成本；不默认有法律迁移收益 |
| R-GCN LawRanker | 候选相关性标注有正/负/未判断，纠纷分组允许验证 | 相同特征线性/MLP vs R-GCN；先不与VerdictNet一起训练 |
| VerdictNet | 有稳定请求标签和上游预测，能做分组交叉拟合 | 相同信息LLM/MLP vs 图网络；结果、理由、校准和成本 |
| 第二个生成模型 | V1链条完成，需判断结论是否仅属于9B | 独立资源检查、独立冻结、同任务关键对照；不得混合为同模型结果 |

GFM-RAG先用作者公开实现/checkpoint的迁移方式，固定revision。若需新增大模型抽图、改变表示或没有适合本机的运行组合，报告适配成本，不偷偷换成另一种图方法。法律断言状态与来源节点必须进入图映射说明。

若之后训练R-GCN，第一组候选可用3层、隐藏256、basis分解4、dropout0.1，AdamW学习率1e-3、权重衰减1e-4、最多50轮、开发组patience5，种子20261001、20261002、20261003。它们是起始配置而非最佳参数；小验证集不足就不做大规模搜索。LawRanker对已判断候选使用成对排序损失，未判断项不作负例；VerdictNet按请求标签训练，类权重仅用训练分布计算。

训练/验证先按已知纠纷组分开，并遵循时间范围。VerdictNet的训练特征用上游在未见该组标签时生成的预测；组数不足以交叉拟合则推迟训练，不把同案条件当独立训练集。可参考[UniLR](https://aclanthology.org/2025.acl-long.584/)的任务相关检索设计，但其训练标签与语料优势不能直接归因到我们的架构。

## 8. 最小交付顺序及仓库协作

按依赖分成以下可审阅提交，具体日程以资源检查的实测耗时为准，不预先承诺9B处理完整数据所需天数。

1. **任务契约与输入范围**：新目录、Schema、来源映射、任务/样本清单；无模型运行即可审阅。
2. **抽取与导入**：MLX入口、新紧凑格式、分块与整理、格式/引用检查；最多2旧案资源检查。
3. **法源与规则**：法源文本单元、BM25与向量/重排、明确规则卡、来源核对记录。
4. **规则应用**：编译器、完整绑定、逻辑组合、未知/反证/例外及必要测试；完成开发链。
5. **冻结与一次比较**：参考隔离、配置与代码快照、E1—E3、分歧预算和完整报告。

每个完成的阶段更新`docs/CHANGELOG.md`；有实际实验时才更新实验索引和最新运行指针。运行`python3 scripts/repository_bridge.py prepare`，检查`review/PUBLICATION.json`，再运行`verify`。公开清单不包含环境、权重、凭据、浏览器截图或批量第三方数据。prepare/verify只生成并核对本地审阅包；只有发布授权范围内的`sync --message ...`才提交推送。

网页审阅包每轮应给出：项目目标、最新源码/数据哈希、允许输入定义、当前方法、实际结果、失败和要审阅的具体问题。ChatGPT的评论保存为待评估建议，不能直接覆盖规则或参考。Codex将确认的问题变成单独修改与必要测试，再发布新版本；网页读取时应报它实际读到的快照。

首个实施动作是提交1并选定开发争点，然后做提交2的资源与格式检查。能够从原文产生可追踪的条件绑定后，再接法源与请求判断。若任一阶段失败，交付该阶段完整结果与明确原因，不靠扩样本、加GNN或反复网页返工掩盖失败。
