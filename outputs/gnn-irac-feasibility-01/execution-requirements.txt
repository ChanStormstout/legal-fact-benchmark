==================================================
七、每个案件必须严格分成两个信息区
==================================================

这是本轮最重要的设计。

A. MODEL INPUT / PRE-OUTCOME SIDE
--------------------------------

只能包含在目标裁判形成前可合理获得的材料，例如：

- parties
- claims / defenses
- pleaded facts
- evidence
- contracts / instruments
- prior procedural findings（若任务允许，必须保留层级）
- factual statement status
- issue
- statutes / precedents available to the court
- source provenance

不得包含：

- target court final conclusion
- target court最终接受/拒绝哪个争点
- winning / losing argument as target-court outcome
- target court final element finding
- target final disposition
- 对目标结果的摘要字段

B. TARGET-CONSTRUCTION / POST-OUTCOME SIDE
------------------------------------------

可以读取历史判决后半部分、法院最终reasoning和现有数据库中的：

- courts_reasoning
- analysis_of_the_law
- conclusion
- accepted / negatively viewed precedent information
- target final findings

但这些信息：

【只能用于构造监督 target 和来源审计】

绝对不能回流到模型input或input graph。

请通过文件/字段级别的 lineage 保存这个隔离，
不能只靠prompt口头说明。

==================================================
八、Rule先使用 reviewed/oracle rule，不做retrieval
==================================================

本轮不要重新研究 authority selection。

每个 pilot 案只选择：

1. governing statute / fixed ground；
2. 必要的、已有来源支持的 legal test / precedent；
3. 必须的 material limitation / counter-rule。

Rule必须有来源。

优先复用我们已经建立的30项authority pool和已有source material，
不要重新网上搜一套全新的法律体系。

如果现有法源不足以构造某个案件的 application target：
明确记录 GAP，
不要为了完成8案自行添加大量新法源。

本轮研究问题必须保持：

【如果Rule已经给对，图结构能否支持Application？】

而不是再次混入 retrieval error。

==================================================
九、Rule decomposition：最小条件/element结构
==================================================

对于每个 reviewed Rule，
只提取本案实际需要判断的条件。

每个 Condition / Element 至少保存：

- id
- rule_id
- exact rule text / source quote
- description
- logical role
- applicable scope / limitation
- dependency（如AND/OR/qualification）
- source citation

不要把一个复杂判例整篇当成一个element。

也不要过度细分成几十个微型条件。

标准是：
该条件能否对应一个有意义的法律判断，例如：

- third party obtained possession
- tenant retained / lost legal control
- written landlord consent exists
- relevant conduct occurred after required date
- legal identity / succession condition
- burden-shift trigger

==================================================
十、Application target
==================================================

每个 element / condition 使用且只使用三个主要状态：

SATISFIED
DEFEATED
UNRESOLVED

含义：

SATISFIED
-----------
历史目标法院明确把该条件视为成立，
且有可定位的目标reasoning依据。

DEFEATED
--------
历史目标法院明确认为该条件不成立，
或有明确相反事实/法律判断击败该条件。

UNRESOLVED
----------
目标材料没有可靠解决，
或者来源不足以区分满足与不满足。

不要把：
“原告没有证明”
机械等同于事实命题为FALSE。

需要区分：
- fact is false
- burden not carried
- not decided
- insufficient record

如果三类无法表达某个已发现的重要情况，
先记录 limitation，
不要立即新增第四、第五种训练类别。

==================================================
十一、Fact → Condition binding
==================================================

每个 element 同时构造候选 binding：

Fact / Evidence
→ SUPPORTS / DEFEATS / RELEVANT_TO
→ Condition

每条 binding 必须保留：

- fact_id
- condition_id
- relation
- statement status
- court / procedural level
- source refs
- whether it belongs to model input
- whether it was used only for target construction

不得根据最终 target label
反向发明一个输入fact。

例如：

如果 target says SATISFIED，
不能为了让链条漂亮而新增：
“tenant lost control”
作为pre-outcome fact，
除非输入材料本身真的这样说。

==================================================
十二、Issue-level conclusion
==================================================

本轮可以额外构造一个 issue-level target，
但它必须与 element target 分开。

建议仅使用：

SUPPORTED
NOT_SUPPORTED
UNRESOLVED

它表示：
在历史目标裁判中，
这个固定issue/ground最终如何处理。

不要直接用WIN/LOSE替代全部element supervision。

如果一个案子存在多个claim，
本轮只处理已经固定的目标issue，
不要扩成整案多请求预测。

==================================================
十三、需要做的source audit
==================================================

8案全部都要做逐链核对，但不是重标整份案件。

每案至少核对：

1. Issue是否真的来自固定研究问题/来源；
2. Rule是否有正确来源；
3. Condition是否忠实于Rule；
4. input Fact是否真的在pre-outcome材料；
5. Fact statement status是否正确；
6. target Application是否有target court reasoning支持；
7. target信息是否错误进入input；
8. conclusion target是否和application target逻辑冲突。

允许普通High辅助审阅。

但：
- 不把High输出称为人工gold；
- 不用模型一致性当正确率；
- 不因为一个案例困难就不断重试到一致。

==================================================
十四、调用预算
==================================================

本轮最多允许：

- 8案 × 1次 application/target proposal = 8次High
- 8案按两批做独立 source review = 2次High
- 如确有必要，可增加最多2次针对性review

总上限：
12次普通High调用。

semantic retry = 0。

失败、分歧、无法判断直接保留。

不要为了让8案全部“成功”无限补调用。

十八、可行性最低标准
==================================================

不要要求8/8完美。

预先使用以下判断：

GO
--
如果至少6/8案件能够形成完整、可追踪、无明显outcome leakage的：
Issue → Rule → Conditions → Facts/Bindings → Application target
链，并且失败不是由同一个系统性schema缺口造成，
建议进入下一轮训练设计。

CONDITIONAL GO
--------------
如果4–5/8可用，
但主要问题是一个有限、明确的adapter或target-construction缺口，
报告最小修复，不自动执行。

NO-GO
-----
如果少于4/8可构造，
或多数target必须靠重写/推测target reasoning，
或pre-outcome/post-outcome无法可靠隔离，
则停止，不训练GNN。

不要降低标准凑数量。
