二、本轮必须解决的已确认问题

1. 局部缺项导致整案拒绝

旧 interface_check 要求每个 binding 都覆盖全部 test_id。1114159 缺一项条件，55384096 的第二组 binding 没有条件记录，均导致整份提议失败。

新的导入器必须区分：
- 整份输出无法解析；
- 某条记录结构或引用无效；
- 某个绑定缺少部分条件；
- 某项语义判断确实未知。

完整 JSON 中的局部缺项不得自动导致整案失败。

保存原始提议，生成单独的导入结果：
- 可读取且引用有效的记录；
- 被隔离的具体记录或连接；
- 模型没有输出的位置及原因；
- 仍可运行的对象组合和条件。

缺少模型输出应标为“未产出”，不能伪装成模型已经判断 UNRESOLVED，更不能补成 REFUTED。程序需要未知占位时，明确它来自缺失输出。

只有无法解析、无法识别必要结构，或没有任何可用提议时，才阻止依赖该提议的方法。技术失败的最终答案保持 null。

2. 生成接口与执行器的编号规则不一致

旧 schema 允许 branch_id 为任意字符串，但执行器只接受模板定义的分支。188721101 把 element_id 填进 branch_id，十条证据用途因此全部被阻止。

从当前法律模板自动生成合法地址目录：
test_id → 允许的 branch_id。

普通条件没有子分支时，使用明确的空分支表示；有分支的条件使用模板中的完整编号。prompt、schema、导入器和执行器使用同一个目录。

优先用当前约束器已支持并经过验证的枚举机制。若不能在 schema 内表达字段之间的全部依赖，至少限制编号候选，并在本地检查组合。不要为此重构 JSON 约束器。

不得根据字符串相似度、编号后缀或模型预期答案，猜测错误编号应该对应哪里。

错误连接只隔离该连接。其原文、对象记录、陈述状态和其他合法用途继续保存。

3. 条件预测与证据判断职责重叠

旧任务要求每项条件都二选一，同时允许 assessment 未决。这给出了“预测被反驳，但证据未知”的双重状态，容易在最终理由中混淆。

本轮修改为：
- 中间条件保留 SUPPORTED / REFUTED / UNRESOLVED / UNSUPPORTED；
- 不再强迫中间条件作二元预测；
- 最终请求预测保留 PREDICT_GRANT / PREDICT_DENY；
- 最终预测必须明确它依赖哪些已知判断、哪些仍属不确定判断。

技术失败仍为 null，不强行生成预测。

不能把“未证明成立”写成“已证明不成立”，也不能把最终预测拒绝解释为全部必要事实都被反驳。

事实和证据提议不必对每个 binding 填完所有条件。已有 conditions 可以改为稀疏记录；程序根据实际记录计算，缺项单独展示。删除重复输出职责，不删除不同对象、反证或关键限制。

4. 程序状态不能冒充法律验证

程序负责：
- 来源定位和恢复；
- 引用、编号及对象连接的结构检查；
- 限制作用范围；
- 同一绑定内已声明条件的组合。

程序不因引用有效就认可事实含义，不因模型标注 PRIOR_COURT_FINDING 就证明归属正确。

保留“基于模型提议计算”的明确标记。程序结果不能强迫最终模型接受错误提议；最终模型仍读取允许原文。

三、修复来源组织，检查模型实际收到什么

对原六案做一次有限的输入映射核对，不重新进行全案标注。

沿下列链条保存对应关系：
原始文书 → 允许片段 → 展示文本 → 实际 prompt → 聊天模板后的输入。

核对：
- 案件身份及目标审理阶段；
- 当事人主张与法院认定是否有必要的归属上下文；
- “he”“the latter”等是否能从提供材料中确定指代；
- 短片段与恢复段落是否重复；
- 否定词、时间、对象及限定是否在处理过程中改变；
- 法源范围和解释限制是否进入实际输入。

“与保存的片段一致”不等于“上下文已充分”，报告需要分别说明。

只允许从已有原文恢复理解当前片段所必需的上下文。新增内容必须有原始位置、恢复理由及输入范围审查，不能加入目标最终理由、最终结论或旧审阅意见。

如果必要上下文与目标答案无法安全分离，明确记录缺口，不为凑完整输入而泄漏答案。

恢复造成允许输入范围变化时，登记新旧差异。这轮属于修改材料组织后的开发验证，不再声称与 V3 是逐字相同输入的纯代码对照。

去重只能处理确定重复：
- 同一来源范围的重复文本只展示一次；
- 旧 source ID 保留可追溯映射；
- 不合并不同陈述者、阶段、对象或含义相近但不相同的陈述；
- 不用模型生成摘要替换原文。

同一案的 A、B、C 必须读取完全相同的修复后案情和法律材料。检查实际提交文件，不能只检查模板。

四、条件含义、对象绑定与输出长度

每个 test_id 必须在输入中对应一条完整、明确的命题。assessment 判断这条命题本身，不判断它对某一方“有利还是不利”。

例如，命题含有“没有其他合适设施”时：
- 当前设施不合适，不等于存在其他合适设施；
- 当前设施不合适，也不自动证明所有其他设施都不存在。

这是通用的量词和否定范围要求，不能直接按关键词翻转标签。不要把 polarity=POSITIVE 简单解释为句子没有否定词。

条件定义继续来自已有模板，不为纠正某案答案改写法律含义。发现模板存在真实歧义时，记录歧义和影响，不偷偷添加法律解释。

最终输出中的 binding 要写清实际人物、房产、事件或安排，不能只重复条件名称。程序可执行的组合继续使用有来源的明确 binding_id，不凭自由文本相似度把不同组合拼起来。

保持现有局部依赖和 AND/OR 语义：
- 一条证据受限，不抹去独立证据；
- 一个择一分支成立，不被其他分支未知封锁；
- 不同事件、合同或对象组合不能各取一个条件拼成成功实例；
- 明确反证和真实冲突必须保留；
- 没找到支持不等于找到反证。

为减少输出负担：
- 提议主要保存对象组合、证据、用途和局部限制；
- 不重复复制长引文；
- 不要求无关或没有依据的条件行；
- 最终回答简短说明决定性条件及主要反对理由；
- 不用紧 maxLength 在句子中间强制结束。

可以替换旧的教学示例，但一次完成并冻结。使用两个短小、完整、与当前案件无关的虚构示例：
- 一个有明确依据支持，且无关分支未知不阻止结论；
- 一个有明确反证，不能仅凭材料缺失得出反驳。

示例展示陈述状态、否定范围和局部未知。不能用112400等目标案件的事实、正确组合或审阅结论作示范。不要让两个例子共同强化“缺信息就拒绝”。

必须覆盖这些真实失败：

同时运行已有修复约束回归和直接相关的tokenizer fixture，不新增模型预跑。测试跳过或实际入口没有接入新逻辑，不能记作通过。

如果结构层仍有已确认错误，先修复并完成上述验收，再开始正式生成。不得以法律结论符合期待作为工程验收条件。

第一部分：两次条件诊断

固定使用112400的C06，只评价条件分析，不预测整个案件。

诊断D-short：
提供C06完整定义、既有相关法源，以及包含人物和审理阶段上下文的必要允许原文。

诊断D-full：
使用完全相同的问题、回答合同和生成设置，但提供修复后的全部允许案情和法律包。

两者回答assessment、对象、来源及简短理由。不得告诉模型正确答案，不输入旧输出或错误清单。两个输入在生成前同时冻结。

短输入与完整输入的信息范围不同，因此不能把差异严格归因于长度。诊断只帮助区分：
- 简洁任务下仍发生方向或归属错误；
- 简洁任务可处理，完整材料下出现整合错误；
- 两者差异可能由新增有效信息解释；
- 两者均未复现旧错误。

不得根据这两次结果修改后续实验。

第二部分：四案恢复比较

固定四案，不按结果换案：
- 112400：条件方向、本人／家属择一路径；
- 188721101：错误分支地址与陈述地位；
- 55384096：局部缺项导致整案隔离；
- 52547606：输出截断及不同阶段法院认定。

每案依次运行：
1. A：完整允许材料，直接给最终回答；
2. P：生成一次结构化提议；
3. B：完整材料＋本轮原样提议，给最终回答；
4. C：完整材料＋同一提议＋程序检查，给最终回答。

共最多16次，加前面的两次诊断，总上限18次。

A/B/C使用相同最终模板与schema。B/C共用同一份提议；语义有错但技术可读的提议保留原样，不能人工修正后再运行。

C的检查展示只做确定性去重。保留不同绑定、支持、反对、未知及限制。不得根据预期答案挑选检查结果，也不要重复嵌入整份提议。

最终请求可以必须给出明确预测，但条件证据状态仍可未知。预测不代表已经证明；理由需要说明不确定因素可能怎样影响选择。不得因缺乏举证规则而编造“法律上必须驳回”的依据。

单个条件失败，只跳过依赖步骤：
- A失败，不阻止P；
- P局部可用，B/C继续并带上覆盖限制；
- P无法解析或完全不可用，B/C保存null并跳过；
- 某案失败，不取消其他独立案件。

资源或框架故障影响后续运行、总时间耗尽时停止。不得加预算、重试、补JSON、换案或继续生成直到出现想要的答案。

七、只做一次集中来源审阅

全部运行结束后，集中审阅两份诊断和最多十二份最终回答。重点检查决定性依据，不重新标注全部中间事实。

使用相同标准：
- 已有事实是否被反写或遗漏；
- 当事人主张是否被当成法院认定；
- 下级法院认定是否保留其阶段和可争议地位；
- 对象、事件、否定及量词范围是否正确；
- 单个住房、单次安排是否被错误扩展为全局判断；
- 择一和同时满足的条件是否混淆；
- 条件状态、解释与最终预测是否一致；
- 真实材料缺口是否与模型遗漏、程序不支持区分；
- 程序检查是否具体纠正了错误，或传播、强化了错误。

不能只检查模型主动引用的段落，也要检查允许材料中的决定性反对依据。

不要求恢复被排除的历史裁判结果。最终标签与历史结果一致，不自动正确；全部回答拒绝，也不自动证明失败或成功。

来源审阅属于模型辅助开发评价，不是人工gold。没有可支持的确定参考，就记录争议，不强行计算法律准确率。

新版本同时改变接口、任务职责、材料展示和提议预算，因此只能评价整组修复后的可用性与答案质量。不能把改善单独归因于某一处修复，也不能据此判断GNN的价值。

八、交付、验收与停止

交付以下内容：

1. 修复表
每个问题的证据、代码位置、修改、真实失败重放结果、剩余限制。明确区分“工程修复通过”与“语义尚未解决”。

2. 实际输入审计
逐案来源到提交文本的映射、恢复或去重记录、范围变化、材料哈希、实际输入tokens和模板化输入。

3. 两项条件诊断
原始答案与来源审阅，说明能排除什么、仍不能确定什么，不用一次诊断宣布模型整体能力。

4. 四案A/B/C比较
技术状态、关键事实和条件、已确认错误、遗漏、内部矛盾、真实缺口及含提议阶段的成本。失败位置保留在表中。

5. 完整运行文件
prompt、schema、raw、parsed、token IDs、finish_reason、实际参数、源码哈希、完整与紧凑检查、失败和停止记录。

6. 简明中文报告
直接回答：
- 局部信息还会不会被整案丢弃？
- 条件方向错误是输入、模型原始输出还是后处理造成的？
- B相对A是否有具体收益？
- C相对B是否有具体收益？
- 哪些错误仍存在，下一步最值得投入在哪一处？

如果工程已通，但模型仍反复误述明确来源，暂停继续增加字段和检查，提出下一轮可验证的模型／任务比较建议，等待决定。若主要仍是输入上下文不足，也应报告具体缺口，不能直接归因于模型弱。

更新CHANGELOG、实验索引、项目状态和审阅包配置，再运行repository_bridge.py prepare，检查发布清单并verify。额外确认prepare之后当前实验入口仍指向本轮，不能只依赖文件哈希一致。

完成必要修复、最多18次调用和一次集中审阅后停止。不得根据新输出继续修prompt、补规则重答、扩大样本、训练GNN、读取SEALED、提交或推送。
